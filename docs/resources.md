## Shared `spec` shapes

The following sub-schemas are carried by every kind that exposes `spec.tooling`,
`spec.hooks` or `spec.guardrails` (Agent, Posture, Skill, Preset). The full
conceptual reference lives in `docs/resources.spec.md`.

### `spec.tooling[*]` — discriminated union on `type`

```yaml
# Route — expose a posture transition as an LLM-callable tool.
- type: route
  name: <tool_name>
  posture: <target_posture>
  description: <intent>           # optional
  params: [...]                   # optional

# Toolset — select tools from named resources, or by label selector.
# `tools` and `selector` are mutually exclusive.
- type: toolset
  tools: ["<resource>/<tools>"]   # OR
  selector: { matchLabels: { ... } }

# Subagent — delegate to another agent.
- type: subagent
  agent_id: <agent_resource_name>
```

### `spec.hooks` — automations per trigger

```yaml
spec:
  hooks:
    on_start:      [{ type: tooluse, tool: <tool>, args: { ... } }, ...]
    on_completion: [...]
    on_tool_use:   [...]
    on_tool_error: [...]
```

Hook variants: `tooluse` (call a tool), `route` (activate a posture), `exit`.

### `spec.guardrails[*]` — assertions on tool calls

```yaml
spec:
  guardrails:
    - name: <unique_local_name>
      appliesTo: "*" | [<tool_names>] | { matchLabels: { ... } }
      assertion: <expression>       # optional
      message: <violation_message>  # optional
```

## `InteractSurface`

- **apiVersion:** `agent/v1`
- **runtime surface:** Permanent (sélectionné via `tools: "<name>/*"`)

### `metadata` _(commun à tous les kinds)_

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `name` | string | yes | — | Identifiant unique de la ressource dans le blueprint. |
| `labels` | map<string, string> | no | — | Labels sélectionnables via `toolset.selector.matchLabels`. |
| `annotations` | map<string, string> | no | — | Annotations libres (non-sélectionnables). |

### `spec`

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `tools` | `"*"` ou liste de strings | no | `"*"` (tous les kinds enregistrés) | Sous-ensemble de tools publiés par la surface. Chaque entrée est un kind discriminant (`ask`, `confirm`, `checklist`, `alert`, `notify`, `prompt`, `display`, `plan`, `announce`) ou un nom de tool complet (`interact__ask`, …). Un nom inconnu provoque une erreur de chargement. |

### Example

```yaml

  name: user
spec: {}                            # publie les 9 tools (ask/confirm/checklist/alert/notify/prompt/display/plan/announce)
```

```yaml

kind: InteractSurface
metadata:
  name: chat
spec:
  tools: [ask, confirm, prompt]     # surface minimale : questions + prompt, pas de notify ni d'affichage riche
```

```yaml

kind: InteractSurface
metadata:
  name: read-only
spec:
  tools: [notify]                   # surface fire-and-forget uniquement
```

### Notes

- Sans `spec.tools` (ou avec `"*"`), la surface publie les neuf tools interact__* (ask/confirm/checklist/alert/notify/prompt/display/plan/announce).
- `spec.tools` accepte un kind (`display`) ou un nom complet (`interact__display`) — les deux pointent sur le même tool.
- Chaque entrée du registre déclare `pinned` : true → délègue à `user-board` (item pinned jusqu'à résolution) ; false → livré immédiatement (fire-and-forget, jamais pinned). `display` est fire-and-forget (rendu HTML brut, pas d'attente).
- `plan` et `announce` sont fire-and-forget ET upsertables : une seule instance vivante par kind, remplacée à chaque appel (le user suit un roadmap évolutif / un focus courant, pas une pile de snapshots ni un log).
- Aucun branchement par nom de kind : notify et prompt passent par le même chemin dans applyTool.
- La réaction post-résolution (ex. `prompt` émet un `UserMessage`) est portée par le hook `reply` de chaque entrée du registre, jamais par le runtime.
- Une surface qui filtre tous ses tools est valide (et juste inutile) — un nom inconnu est une erreur de chargement explicite.
- Aucun effet tant qu'aucune entrée `toolset` ne la sélectionne.
